# สำรองและทดลองกู้คืน MONSTOPIA

## สำรองอะไรและทำไม

ฐานข้อมูลเก็บข้อมูลผู้ใช้ บรีฟ โครงการ และตำแหน่งไฟล์ แต่ไม่ได้เก็บเนื้อหาไฟล์แนบ การสำรองเฉพาะ SQL จึงไม่พอสำหรับกู้คืนงานจริง คำสั่งใหม่สำรอง SQL และไฟล์ทุกไฟล์ที่มีรายการใน `project_attachments` ทั้งไฟล์ลูกค้าและไฟล์ภายในทีม พร้อม SHA-256 สำหรับตรวจว่าคัดลอกครบและไม่เสียหาย ไม่สำรอง `.env` และไม่ส่งข้อมูลขึ้น GitHub หรืออินเทอร์เน็ต

จาก Terminal ที่ `D:\motopia`:

```powershell
.\.runtime\php\php.exe artisan monstopia:backup-all
```

ชุดใหม่อยู่ที่ `storage/app/private/backups/bundle_*` ประกอบด้วย:

- `monstopia_*.sql.gz`: โครงสร้างและข้อมูล MySQL
- `files/*.bin`: เนื้อหาไฟล์แนบจริง ไม่ใช้ชื่อไฟล์จากผู้ใช้เป็นชื่อปลายทาง
- `manifest.json`: เวลาสำรอง ตำแหน่งไฟล์ ขนาด SHA-256 และจำนวน/ลายนิ้วมือข้อมูลแต่ละตาราง

เมื่อสำเร็จเท่านั้นจึงมี manifest สถานะ `complete` หากพบไฟล์หายหรือข้อมูลเปลี่ยนระหว่างสำรอง คำสั่งแจ้งล้มเหลวและไม่รับรองชุดนั้น ควรสำรองในช่วงที่ไม่มีการแก้ไขข้อมูล และห้ามเปลี่ยน schema ระหว่างสำรอง การสำรองไฟล์กับ MySQL ไม่ใช่ transaction เดียวกัน จึงยังต้องวางแผนช่วงหยุดเขียนข้อมูลเมื่อใช้งานจริงจำนวนมาก

`monstopia:backup-database` เดิมยังใช้ได้ แต่สำรอง SQL เท่านั้น ไม่มีการลบชุดเก่าอัตโนมัติในคำสั่งปกติ หากต้องการลบ SQL-only เก่าตาม `BACKUP_RETENTION_DAYS` ต้องระบุ `--prune` เอง ชุด bundle เก่าไม่ถูกลบโดยระบบนี้ ต้องตรวจและเลือกนโยบายเก็บรักษาเอง

สำรองแบบ mysqldump ใช้ InnoDB consistent snapshot; หาก binary ใช้ไม่ได้ ตัวสำรอง PHP ใช้ REPEATABLE READ transaction และอ่านข้อมูลเป็นชุด ลดการใช้หน่วยความจำ ตัวสำรอง PHP เหมาะกับตารางของ Laravel ไม่ใช่ตัวแทนการสำรอง stored routines/events/views/trigger ที่เพิ่มเองในอนาคต ต้องตรวจและใช้ mysqldump ให้สำเร็จหากเพิ่มองค์ประกอบเหล่านั้น

## ตั้งสำรองอัตโนมัติบน Windows

เปิด MySQL และทดลอง `monstopia:backup-all` ให้ผ่านก่อน จากนั้น:

```powershell
powershell -NoProfile -File .\Install-MONSTOPIA-BackupTask.ps1 -WhatIf
powershell -NoProfile -File .\Install-MONSTOPIA-BackupTask.ps1
```

ตัวติดตั้งสร้าง Task Scheduler ชื่อ `MONSTOPIA Daily Backup` เวลา 02:00 ตาม Windows timezone กรุงเทพฯ และตรวจสำรองตกหล่นตอนเข้า Windows หากเพิ่งสำรองสำเร็จใน 22 ชั่วโมงจะไม่ทำซ้ำ เก็บ Log ใน `storage/logs/backup-YYYY-MM-DD.log` ไม่เก็บรหัส Windows และรันแบบหน้าต่างซ่อน ไม่ทับ Task ที่มีชื่อเดียวกันอยู่แล้ว

ข้อจำกัด: เครื่องต้องเปิดและต้องมีผู้ใช้ Windows ลงชื่อเข้าใช้ เพราะเลือก Interactive logon เพื่อไม่ต้องเก็บรหัสผ่าน ระบบจะพยายามใหม่หลังผิดพลาด 3 ครั้งทุก 15 นาที ตัว runner เปิด bundled MySQL แบบหน้าต่างซ่อนให้ได้เฉพาะเมื่อ Laravel ใช้ MySQL ในเครื่องพอร์ต 3306 และพอร์ตยังไม่ทำงาน ไม่เปิดเว็บเซิร์ฟเวอร์ ไม่สั่ง migration และไม่เริ่ม server ใดหากใช้ฐานข้อมูลนอกเครื่องหรือพอร์ตอื่น ไม่ใช่บริการสำรองตลอด 24 ชั่วโมง สำหรับ Hosting/VPS ใช้ cron เรียก `php artisan schedule:run` ทุกนาทีแทน ไม่ต้องเปิด cron และ Windows task สำหรับระบบเดียวกันพร้อมกัน

Laravel Scheduler เปลี่ยนเป็น `monstopia:backup-all` ทุกวัน 02:00 ตาม `MONSTOPIA_BUSINESS_TIMEZONE=Asia/Bangkok` แล้ว แต่การมี Schedule ในโค้ดอย่างเดียวไม่ได้ทำให้รันเอง

## เก็บนอกเครื่อง

เพิ่ม `BACKUP_EXTERNAL_DIRECTORY` ใน `.env` เฉพาะเมื่อมีปลายทางที่คุณเลือกแล้ว เช่น absolute path ของไดรฟ์สำรอง (`E:/MONSTOPIA-Backups`) หรือ network drive ที่ map เป็นตัวอักษรไดรฟ์และได้รับอนุญาตแล้ว (ไม่รองรับ UNC path แบบ `\\server\share`) คำสั่งจะคัดลอกชุดใหม่และเทียบ SHA-256 ทุกไฟล์ ไม่สร้างบัญชี cloud หรือส่งให้บริการใดโดยอัตโนมัติ

โฟลเดอร์อื่นบนดิสก์ลูกเดียวกันไม่ใช่สำรองนอกเครื่องจริง หากดิสก์เสียทั้งสองชุดอาจหายพร้อมกัน ควรใช้ดิสก์แยกหรือบริการที่คุณควบคุม ตรวจสิทธิ์การเข้าถึง และเข้ารหัสอุปกรณ์สำรอง เพราะ SQL มีอีเมลลูกค้าและ password hash; `.env` กับ `APP_KEY` ต้องเก็บแยกในที่ปลอดภัย ชุดนี้ยังไม่เข้ารหัสเอง บน Windows ต้องตรวจ NTFS permissions ของโฟลเดอร์เองด้วย เพราะ `chmod` ของ PHP ไม่ใช่การตั้ง Windows ACL

หากคัดลอกปลายทางภายนอกไม่สำเร็จ คำสั่งคืนสถานะล้มเหลวแม้ชุดในเครื่องสร้างเสร็จแล้ว ให้ตรวจ Log/ไดรฟ์และลองใหม่ ห้ามเก็บชุดสำรองใน `public`

## ทดลองกู้คืนไฟล์โดยไม่ทับของจริง

ใช้เฉพาะชุดสำรองที่เราเป็นผู้สร้างและเชื่อถือได้ ไม่ใช้ SQL/manifest ที่ได้รับจากคนอื่น:

```powershell
.\.runtime\php\php.exe artisan monstopia:verify-backup "D:\motopia\storage\app\private\backups\bundle_ชื่อชุดจริง" --files-only
```

คำสั่งตรวจ checksum ของ SQL และไฟล์แนบ จากนั้นคัดลอกไฟล์ไปโฟลเดอร์ใหม่ `storage/app/private/restore-tests/restore_qa_*` และตรวจ checksum หลังคัดลอกอีกครั้ง ไม่เขียนกลับ Storage เดิม ไม่ลบชุดสำรอง ไม่แตะไฟล์ลูกค้าจริง หากมีข้อมูลจริง ผลทดสอบกู้คืนก็เป็นข้อมูลลับเช่นกัน

`--files-only` **ไม่ได้ยืนยันว่าฐานข้อมูลนำเข้าได้** และ `files_verified: 0` หมายถึงไม่มีไฟล์แนบในชุดนั้น ไม่ใช่หลักฐานว่าทดลองกู้คืนไฟล์งานจริงแล้ว

## ทดลองกู้คืนฐานข้อมูลพร้อมไฟล์

ต้องเตรียม MySQL server ทดสอบแยก instance จากระบบจริง เช่นพอร์ต 3307 และ data directory ใหม่ ห้ามใช้ instance พอร์ต 3306 ของงานจริง ตั้งค่าต่อไปนี้ใน environment ของ Terminal ทดสอบหรือ `.env` โดยเก็บรหัสให้ปลอดภัย:

```dotenv
MONSTOPIA_RESTORE_HOST=127.0.0.1
MONSTOPIA_RESTORE_PORT=3307
MONSTOPIA_RESTORE_USERNAME=บัญชีของ-server-ทดสอบ
MONSTOPIA_RESTORE_PASSWORD=รหัสของ-server-ทดสอบ
```

จากนั้นเรียกคำสั่งเดิมโดย **ไม่ใส่ `--files-only`** คำสั่งตรวจ MySQL `server_uuid` และปฏิเสธ instance เดียวกับระบบจริง สร้างฐานข้อมูลชื่อใหม่ที่ระบบสุ่มเอง `monstopia_restore_qa_*` (ใช้ CREATE DATABASE โดยไม่ใช้ IF NOT EXISTS) จึงไม่เลือกหรือเขียนทับฐานข้อมูลที่มีอยู่

ตรวจว่าข้อมูลทุกตาราง จำนวนแถว และโครงสร้าง/index/foreign key ตรง manifest หลังนำเข้า พร้อมสร้าง `verification.json` ในโฟลเดอร์กู้คืนใหม่ ออกจากคำสั่งโดยสำเร็จต่อเมื่อทุกจุดผ่าน หากผิดพลาดอาจเหลือโฟลเดอร์/ฐานข้อมูลทดสอบใหม่ไว้เพื่อวิเคราะห์ ไม่ลบแบบ recursive และไม่ลบข้อมูลจริง

ผลทดสอบนี้ตรวจ SQL และไฟล์เทียบชุดสำรอง ไม่ใช่การรับรองว่าใช้งาน Production ได้ทั้งหมด ยังต้องทดสอบ Login/API บนระบบที่กู้คืนจริง และวางแผนกู้คืน `.env`, `APP_KEY`, โค้ด, รูป public, สิทธิ์ไฟล์ และอีเมลด้วย
